Design decisions
  • Incremental MERGE loads into Delta tables, with historical snapshots: rerunning a job never duplicates data.
  • Per-file reprocessing: only the plans that change are loaded again.
  • Serverless compute: no cluster stays on between runs, so only execution time is paid for.
  • Jobs as code, with a final SQL test task (96 tests on the course model) that stops the job and alerts on any failure.
  • Separate development and production: production is reached only through merge requests.
How it runs

The jobs run every day with no manual work, and survey audiences are generated automatically from the academic calendar. The same architecture, with public code and fictional data, is in Academic calendars on Databricks.

Pipelines on AWS

  • Academic calendars on Databricks

    Takes the calendars that a fictional company's partner universities drop in S3 through bronze, silver and gold Delta tables on Databricks. Files that have not changed are skipped, and rows that cannot be used are set aside with the reason.

    • Decision: Bronze stores a SHA-256 fingerprint of each file and only appends what changed: running the job ten times leaves the tables the same. It runs on serverless, with one catalog per environment.
    • Quality: unusable rows go to a rejects table with their reason, without stopping the load; Gold fails if two periods of a cohort overlap and leaves the previous table intact.

    Code: bronze.py · silver.py · gold.py · databricks.yml

  • FinTrust data pipeline

    Replaces manual report downloads at a consumer-credit fintech with an automated pipeline in BigQuery, with documented technical decisions and data-quality evidence.
